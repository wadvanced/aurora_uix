# Getting Started

Welcome to **Aurora UIX**! This guide helps you add Aurora UIX to your Phoenix project and build your first CRUD UI with minimal code.

Aurora UIX is a low-code framework for building dynamic, metadata-driven UIs in Phoenix LiveView applications. It lets you define schema metadata once and automatically generate complete CRUD interfaces.

> #### New to Elixir or Phoenix? {: .tip}
> This guide assumes you already have a Phoenix project. If you're starting from
> scratch, follow the [Build Your First App](../tutorial/build_your_first_app.md)
> tutorial first — it installs the toolchain and builds a complete app from
> nothing, then sends you back here for the details.

The setup has five steps, in order:

1. [Install the dependency](#installation)
2. [Add the stylesheet](#css-configuration)
3. [Set up the icons](#icons-configuration)
4. [Import the JavaScript hooks](#javascript-setup)
5. [Describe a resource, lay out its views and add the routes](#basic-usage)

## Installation

Add `aurora_uix` to your `mix.exs` dependencies. Make sure your Phoenix project is using Phoenix 1.8+ and Phoenix LiveView 1.2+:

```elixir
def deps do
  [
    {:aurora_uix, "~> 0.2.1"}
  ]
end
```

Aurora UIX needs `phoenix_live_view ~> 1.2`. Some `mix phx.new` releases write an older requirement
(`~> 1.1.0`), and dependency resolution then fails. Raise it in your `mix.exs`:

```elixir
{:phoenix_live_view, "~> 1.2"},
```

Then fetch the dependencies:

```shell
mix deps.get
```

## Formatter

Aurora UIX exports the calls of its DSLs (`schema`, `label`, `backend_opts`, `rule`, `inline`, ...) so
`mix format` keeps them without parentheses. Import them in your `.formatter.exs`:

```elixir
[
  import_deps: [:aurora_uix],
  # ...
]
```

Without it, `mix format` rewrites `ash_resource Employment` as `ash_resource(Employment)`, and keeps the
parentheses afterwards.

## CSS Configuration

Aurora UIX renders its UI with CSS themes. The `basic` template includes three, each in light and
dark: White Charcoal (the default), Vitreous Marble and Blue Graphite. See the
[Theming](../customization/theming.md) guide to choose one.

To enable Aurora UIX styling, generate the stylesheet and import it in your application's CSS:

> #### Pure CSS: Tailwind and daisyUI are optional {: .info}
> Aurora UIX styles its components with pure CSS: `--auix-*` custom properties and `.auix-*` rules
> in native cascade layers, with no Tailwind utilities, `@apply` or build plugin. That is
> deliberate, so a host can adopt the styles however its own CSS is built: through Tailwind v4,
> another bundler, or plain stylesheets, and map them onto any design system with a bridge. The
> steps below are written for Tailwind v4, the default in a new Phoenix application.
> Without Tailwind, see [Hosts without Tailwind](../customization/styling.md#hosts-without-tailwind);
> with Tailwind v3, see [Tailwind v3 hosts](../customization/styling.md#tailwind-v3-hosts).

### Step 1: Generate the Stylesheet

Run the stylesheet generator task:

```shell
mix auix.gen.stylesheet
```

This generates these files under `assets/css/`:

- `auix-variables.css` — `:root` declarations for all `--auix-*` custom properties (sizes, colors, shadows).
- `auix-rules.css` — the `.auix-*` component rules that consume those variables.
- `auix-stylesheet.css` — a shim that imports the two files above.
- `auix-bridge-daisyui.css` — the daisyUI bridge of Step 3 below, copied on the first run only.

### Step 2: Import Stylesheets in app.css

In your `assets/css/app.css`, after your own imports, add the variables, then any overrides, then
the rules:

```css
/* Your custom styles and other imports go here */

@import "./auix-variables.css";     /* Aurora UIX defaults */
:root { /* optional: override --auix-* vars here */ }
@import "./auix-rules.css";
```

> #### Keep the `./` and the order {: .warning}
> Tailwind v4 resolves an import without `./` as a package and fails with `Can't resolve
> 'auix-variables.css'`. Keep variables first and rules last, so the overrides you place between
> them take effect.
>
> `auix-stylesheet.css` imports the other two with `./`, so `@import "./auix-stylesheet.css";` also
> works when you have no overrides to place between them. A copy generated by an earlier version
> imports them without `./`: re-run `mix auix.gen.stylesheet` to regenerate it.

The stylesheets are bundled with your application CSS and served with your other assets, through
the stylesheet link your root layout already has:

```html
<link phx-track-static rel="stylesheet" href={~p"/assets/css/app.css"} />
```

> #### Regenerating After Theme Changes {: .info}
> If you change your Aurora UIX theme configuration, re-run `mix auix.gen.stylesheet` to update the generated stylesheets.
>
> **Note**: This command is also used when creating custom themes. See the [Creating Custom Registered Themes](../customization/theming.md) guide for details on building your own themes.

### Step 3 (optional): Inherit the host's daisyUI theme

If your Phoenix app uses Tailwind v4 + daisyUI, Aurora UIX can follow the host theme automatically. The first time you run `mix auix.gen.stylesheet` it also copies a bridge file — `assets/css/auix-bridge-daisyui.css` — a small mapping that connects daisyUI tokens (`--color-primary`, `--color-base-100`, `--radius-field`, …) to `--auix-*` variables. Import it between the variables and the rules:

```css
@import "tailwindcss";
@plugin "daisyui";

@import "./auix-variables.css";       /* Aurora UIX defaults */
@import "./auix-bridge-daisyui.css";  /* inherit daisyUI theme */
:root { /* optional host overrides */ }
@import "./auix-rules.css";           /* must be last */
```

Switching the daisyUI theme (or toggling dark mode) then automatically restyles every Aurora UIX component with no further mix tasks. The bridge file is yours to edit — subsequent runs of `mix auix.gen.stylesheet` leave it untouched. Run with `--force` to refresh it from the library version:

```shell
mix auix.gen.stylesheet --force
```

If you use a design system other than daisyUI, see the [Writing a Style Bridge](../customization/writing_a_style_bridge.md) guide to create your own mapping.

## Icons Configuration

Aurora UIX uses **Heroicons** for its icons, as `hero-*` CSS classes. Set them up in one of two
ways.

### If Your Application Already Uses Heroicons

A new Phoenix application does: it has the `heroicons` dependency and a Tailwind plugin that
creates the classes. Add this line to your `assets/css/app.css`, so Tailwind includes the classes
Aurora UIX uses without scanning the dependency:

```css
@source "../../deps/aurora_uix/priv/static/classes.js";
```

### If It Does Not

Add the `heroicons` dependency, which Aurora UIX does not bring with it:

```elixir
{:heroicons,
 github: "tailwindlabs/heroicons",
 tag: "v2.2.0",
 sparse: "optimized",
 app: false,
 compile: false,
 depth: 1}
```

Then fetch it and generate the icon classes:

```shell
mix deps.get
mix auix.gen.icons
```

This writes `assets/css/auix-icons.css` with every Heroicon as a CSS class (`.hero-{icon-name}`,
`.hero-{icon-name}-solid`, `.hero-{icon-name}-mini`, `.hero-{icon-name}-micro`). Import it in
`assets/css/app.css`:

```css
@import "./auix-icons.css";
```

> #### Using Custom Icons {: .info}
> If you need to add your own icon classes or modify the generated ones, edit `assets/css/auix-icons.css` directly. Re-running `mix auix.gen.icons` will overwrite this file, so keep a backup of any custom changes.

## JavaScript Setup

Aurora UIX ships client-side hooks and event listeners in `assets/js/hooks.js`. Host applications
must import this file in their own `assets/js/app.js` so the browser can receive events pushed by
the server (e.g. file downloads from upload fields) and activate hooks (e.g. the theme switcher on
index pages).

Add the import, and spread the hooks into your `LiveSocket` next to the ones you already have. In
a Phoenix 1.8 application:

```js
import {hooks as colocatedHooks} from "phoenix-colocated/my_app"
import {Hooks as auroraHooks} from "../../deps/aurora_uix/assets/js/hooks.js"

const liveSocket = new LiveSocket("/live", Socket, {
  longPollFallbackMs: 2500,
  params: {_csrf_token: csrfToken},
  hooks: {...colocatedHooks, ...auroraHooks},
})
```

Rebuild your assets after adding the import:

```shell
mix assets.build
```

> #### What does this enable? {: .info}
> - **`AuixThemeName` hook** — sets the active theme on `<html>` (`data-theme-name`) for the generated
>   pages and the embedded components.
> - **`AuixCopyToClipboard` hook** — the copy button of copyable inputs.
> - **`phx:auix_download` listener** — performs browser file downloads for upload fields configured
>   with a `:download` callback. Without this import, clicking the Download button on a show or edit
>   page will silently do nothing.

## Basic Usage

Aurora UIX works in three main steps:

### 1. Define Resource Metadata

Resource metadata describes the UI characteristics of the fields of an Ecto schema or an Ash
resource. Use the `auix_resource_metadata` macro to configure how each field is rendered. This
example uses an Ecto schema and its context; for Ash, see the
[Ash Integration](../core/ash_integration.md) guide. The context needs the CRUD functions Aurora UIX
looks for, which [`aurora_ctx`](https://hexdocs.pm/aurora_ctx) generates (see
[the tutorial](../tutorial/build_your_first_app.md#option-a-phoenix-and-ecto)).

```elixir
defmodule MyAppWeb.ProductViews do
  use Aurora.Uix

  alias MyApp.Inventory
  alias MyApp.Inventory.Product

  auix_resource_metadata :product do
    context Inventory
    schema Product
    field :name, placeholder: "Product name", length: 40, required: true
    field :description, length: 255
    field :price, precision: 12, scale: 2, readonly: true
  end
end
```

This tells Aurora UIX:
- How to label and validate fields
- What input types to render (text, number, checkbox, etc.)
- Which fields are required, readonly, or hidden

For detailed configuration options, see the [Resource Metadata Guide](../core/resource_metadata.md).

> **Using Ash with policies?** If your resource is protected by
> `Ash.Policy.Authorizer`, add `backend_opts: [ash_actor_assign: :current_user]` to thread the
> current user as the Ash actor on every generated CRUD call. See
> [Ash Integration → Authorization and policies](../core/ash_integration.md#authorization-and-policies).

### 2. Generate UI Layout

In the same module, use the layout DSL to define which fields appear in your index (list), show,
and form views. You can use the defaults or customize the layout:

```elixir
  auix_create_ui do
    index_columns :product, [:name, :price]
    edit_layout :product do
      inline [:name, :price, :description]
    end
  end
```

For more layout options, see the [Layouts Guide](../core/layouts.md).

### 3. Add Routes to Router

Add the generated LiveView to your router. Each resource gets one routable LiveView,
`<ViewsModule>.<Schema>.Index`, and the action of the route selects the view. Use the route helper:

```elixir
import Aurora.Uix.RouteHelper

scope "/inventory", MyAppWeb do
  pipe_through :browser

  auix_live_resources "/products", ProductViews.Product
end
```

It expands to these routes, which you can also write yourself. Give every route its action: a route
without one raises when it is visited.

```elixir
scope "/inventory", MyAppWeb do
  pipe_through :browser

  live "/products", ProductViews.Product.Index, :index
  live "/products/new", ProductViews.Product.Index, :new
  live "/products/:id/edit", ProductViews.Product.Index, :edit
  live "/products/:id/show", ProductViews.Product.Index, :show
  live "/products/:id/show-edit", ProductViews.Product.Index, :show_edit
end
```

`:show_edit` is the edit form opened from the show view.

<a id="only-some-routes"></a>

#### Only Some Routes

Generate some of the routes with `only:` or `except:`. The route actions are `:index`, `:new`,
`:edit`, `:show` and `:show_edit`:

```elixir
# Read-only interface: no create or edit routes
auix_live_resources "/products", ProductViews.Product, only: [:index, :show]

# The same routes, naming the ones to leave out
auix_live_resources "/products", ProductViews.Product, except: [:new, :edit, :show_edit]
```

These options only choose routes. The buttons that lead to a missing route still render, and
deleting is an event, not a route, so remove those actions in the layout too:

```elixir
auix_create_ui do
  index_columns :product, [:name],
    remove_header_action: :default_new,
    remove_row_action: :default_row_edit,
    remove_row_action: :default_row_delete,
    remove_selected_action: :default_selected_delete_all

  show_layout :product, remove_header_action: :default_edit do
    stacked [:name]
  end
end
```

Removing routes and buttons is not authorization: enforce permissions in your context functions or
Ash policies.

#### A Renamed LiveView

A LiveView renamed with an `index_live` line (see
[Naming and reusing generated modules](../core/components.md#naming-and-reusing-generated-modules))
is routed with `index_live:`:

```elixir
auix_live_resources "/catalog", ProductViews.Product, index_live: :catalog
```

### Run Your App

Start your Phoenix server and navigate to the defined paths to see your complete CRUD UI:

```shell
mix phx.server
```

Visit `http://localhost:4000/inventory/products` to see your generated interface with list, detail, create, and edit views.

## Live Updates (optional)

Name your application's PubSub server so every generated index updates when data changes in
another session:

```elixir
# config/config.exs
config :aurora_uix, pubsub_server: MyApp.PubSub
```

Use the server your Phoenix application already starts (`{Phoenix.PubSub, name: MyApp.PubSub}`
in `application.ex`). Without this key the generated views work as before, and only the
session that made a change refreshes. See
[LiveView Integration › Reacting to Data Changes](../core/liveview.md#reacting-to-data-changes).
