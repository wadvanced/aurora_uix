---
name: prepare-release
description: >
  Prepare a release of aurora_uix up to and including the pull request: bump
  the version, finalize the CHANGELOG, refresh README/ROADMAP/guides, rebuild
  the assets, regenerate and review the guide screenshots, run the quality
  gate, check the Hex package and open the PR. Use this skill when the user says
  "prepare release", "prepare 0.x.y", "release 0.x.y", "cut a release" or "get
  the release ready". It never merges, tags or publishes.
---

Turns the current `@version` (typically `0.x.y-rc.N`) into the release version
and opens one PR carrying everything the release needs. The skill **ends at the
opened PR**: merging, tagging, publishing to Hex and any other post-release work
are not part of it and are never started from here.

Follows `../shared/turn-discipline.md` throughout. Gates run through
`.claude/scripts/gate.sh` / `suite.sh` as `../shared/background-long-commands.md`
says (start with `run_in_background`, wait once with `wait-verdict.sh`).

**Input**: the target version. Default: the current `@version` in `mix.exs` with
the `-rc.N` suffix removed. Call it `<ver>` below; `<today>` is today's date
(`YYYY-MM-DD`).

## 0. Preflight

1. Read the release issue and its parent; every blocker listed there must be
   `CLOSED` (`gh issue view <n> --json state`). Any open blocker → stop and report.
2. `git status` must be clean. Never work on `main`: branch off `origin/main`
   (`git fetch origin && git checkout -b federico/release-<ver> origin/main`).
   If already on a non-`main` branch, stay on it.
3. Environment: `mix deps.get`; `scripts/test_pg.sh ensure`;
   `MIX_ENV=test mix ecto.create && MIX_ENV=test mix ecto.migrate` (migrations
   are not run by `mix test`); `which chromedriver` (Wallaby needs it for step 5).

## 1. Version bump

- `mix.exs`: `@version "<ver>"`. On macOS use `sed -i ''` (BSD sed), or Edit.
- Find stale mentions and fix the install snippets:
  `grep -rnE "0\.[0-9]+\.[0-9]+" README.md CONTRIBUTING.md guides mix.exs`
  The `{:aurora_uix, "~> x.y.z"}` snippets (README.md, `guides/introduction/getting_started.md`,
  `guides/core/ash_integration.md`) take the new version. Leave historical
  mentions (older CHANGELOG releases, "pre-x.y.z look" notes).
- Final check, must print nothing: `grep -rn "<ver>-rc\|~> <previous>" README.md guides mix.exs CONTRIBUTING.md`.

## 2. CHANGELOG

- `## [<ver>]` → `## [<ver>] - <today>` (same shape as the older headings).
- There is no per-rc heading; confirm the section is one consolidated list
  (Fixes / Added / Changed / Documentation) with no duplicated entries.
- Every merged feature/fix of the release must have an entry — compare against
  `git log <previous-tag>..origin/main --oneline`. Tests-only work needs none.
- Rewrite the bold subtitle and intro paragraph so they cover the whole release,
  not just its first feature.
- Entries carry no issue-link suffix (`[#343](...)`); that is the convention for
  new entries.

## 3. Other docs

- `ROADMAP.md`: "Current Status" → `v<ver>` with a one-paragraph summary and a
  "Recent Changes" list; the former current release becomes "Previous Release",
  the one before "Earlier Release".
- `CONTRIBUTING.md`: version mentions, if any.
- Every `guides/**/*.md` must be in `docs.extras` of `mix.exs`:
  `for f in $(find guides -name '*.md'); do grep -q "\"$f\"" mix.exs || echo "NOT IN EXTRAS: $f"; done`

## 4. Build assets

`mix assets.build`

Required before any screenshot: it regenerates icons, the theme stylesheet
(`assets/css/auix-*.css`, gitignored and **not** regenerated by `mix consistency`),
esbuild bundles and digests. Without it the capture tests serve stale CSS/JS and
the images would not show the real UI. It must exit `0`.

## 5. Screenshots

`mix test test/guides/capture_*.exs`

Overwrites the PNGs in `guides/overview/images`, `guides/core/images/layouts`
and `guides/core/images/ash` (desktop 1024×768, mobile 412×915) through
`ImageHelper.capture/5`. Capture tests pass even when an image is visually wrong,
so review the output:

1. `git status --short` — only `.png` files under those three directories change
   (an unchanged one means byte-identical, which is fine).
2. **Read every changed PNG** (at least one per capture file, all of the
   index/show/edit views) and check: current UI features are visible (e.g. sort
   arrows on index headers), data is the expected sample data, no error flash or
   half-loaded state, no clipped or empty crop, modal and tabs render as the
   guide text describes.
3. A new feature that deserves a picture: add a capture to
   `test/guides/capture_*.exs`, re-run, and reference it from the guide with the
   existing `<img src="./images/..." width="600" alt="...">` pattern.
4. A bad capture → fix the capture test or the UI, rebuild if CSS/JS changed
   (step 4), re-run. Do not hand-edit PNGs.

## 6. Quality gate

1. `.claude/scripts/gate.sh` → must end `EXIT: 0` (consistency stages; the
   `docs/spec-only` skip does not apply, `mix.exs` changed).
2. `.claude/scripts/suite.sh` → must end `EXIT: 0`.
3. `mix docs` → exit `0` and no `warning` lines (broken extras, links, images).

## 7. Package check

`mix hex.build` — read the file list: `lib`, `assets/js`, `priv/static/css`,
`priv/static/classes.js`, `README.md`, `CHANGELOG.md` present; nothing from
`lib/aurora_uix/guides/`. Then delete the generated `aurora_uix-<ver>.tar`.
This builds only; it publishes nothing.

## 8. Commit and PR

1. Commit with conventional commits, separating the concerns:
   `chore: release <ver>` (mix.exs, CHANGELOG, README, ROADMAP, guide text) and
   `docs: regenerate guide images` (the PNGs and capture-test changes). `gate-commit`
   can do the grouping.
2. Open the PR with `do-pr`, referencing the release issue. The PR body lists the
   screenshots regenerated and the gate/suite/docs results.
3. Report the PR URL and stop.
